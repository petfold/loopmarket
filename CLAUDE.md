# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

`loopmarket` is a **universal combinatorial marketplace**: every economic intention is one uniform, content-addressed **offer** (a thing described as a conjunction of OntoDAG categories, a service time window, a service region, a validity window — priced on the maker's **personal scale**, a pure-bookkeeping numeraire that the record encoding calls the maker's personal token: nothing is ever held or transferred, the numbers cancel in-loop); a distributed **offer book** holds them as a versioned recordstore keyspace (Swarm-backed in deployment); competing **solver agents** hunt profitable **loops** (cycles whose exchange-rate product exceeds 1 ⇔ negative cycles under −log weights — the P0 case; the general cleared object is a value-conserving **circulation** with composed legs, `docs/plans/P2-loop-selection.md` §11, reframed 2026-09-07); a **clearing** layer re-verifies every proposed loop from scratch and commits all its legs atomically. The full design rationale — including the parts deliberately not built yet — is in `ARCHITECTURE.md`. Read it before structural changes. The forward design corpus (P1–P4 work packages, threat register, catalogue bootstrap, factbond coupling) lives under `docs/plans/` — indexed on the front page, `README.md` (doc table, phase↔doc map, reading order); planned invariants U8–U14 are specified there and enter this file only when their enforcing code and tests land (U11 entered 2026-08-20).

The conceptual background is the "Loop Economy" essay (offers, loops, bridges, bonds, nano-bets, solver ecology). This repo is phase P0 of that programme: the in-memory/prototype track that must stay runnable end-to-end at all times.

## The stack and its direction

```
loopmarket  →  ontodag (>=0.26.1)  →  recordstore (>=0.16.0)  →  Swarm (optional)
```

- **ontodag** (github.com/petfold/ontodag): the shared catalogue. One query primitive — intersection of descendant cones, `get(terms, items_only=True)` (Peter, 2026-09-12: *ontodag is based on intersection*; a want is the wider cone, a give the narrower — an overlap query mode was built and withdrawn that day). `Ontology` in `src/loopmarket/ontology.py` is a thin matching-oriented facade (`covers`, `satisfies` over `OntoDAG.is_below`) and the place where pinned catalogue roots surface. Identity at ontodag's public boundary is the *name* (plain strings accepted anywhere an `Item` is). **Pin (2026-09-13):** `ontodag>=0.26.1` — the release that carries the graph kind (#19: `transport(small-item weight(..8kg))` as a term the graph orders), after 0.25.0's #14, #15, #16.
- **recordstore** (github.com/petfold/recordstore): the book's kernel. Canonical roots (equal content ⇒ equal reference), snapshot isolation via `RecordStore.at(root, blobs)` (note: the blob-store attribute is **`.blobs`**), three-way `merge`, `commit(reconcile=True, resolver=...)` for multi-writer convergence. The interface summary lives in ontodag's `docs/recordstore-interface.md`; treat it as the API reference.
- **Swarm**: reached only through recordstore (`BeeBytesStore` + `SwarmFeedPointer`, assembled by `swarm_store(topic, signer=/owner=)`). `registry.swarm_offer_book()` and `Ontology.persistent()` are the only places that name it.

## Dependency boundaries (tests/test_boundaries.py — must always pass)

- **B1 The core works offline.** `import loopmarket` and the whole model (schema, ontology, matching, graph, solver, mock clearing) must function with no network, no Bee node, and no optional dependency. Swarm is a persistence backend chosen at the edges, never a requirement of the model.
- **B2 One-directional dependencies.** loopmarket imports ontodag and recordstore; never the reverse, and never `requests`/`swarm_bee` at module import time (they load lazily inside the Swarm call paths, as in recordstore itself).

## Core invariants (do not weaken; add tests when touching them)

- **U1 Uniform offer form.** Exactly one side of every `Offer` is a `Thing`, exactly one is `Tokens`, and the token issuer **is** the maker. Enforced in `Offer.__post_init__`; the whole loop arithmetic depends on it.
- **U2 Offers are immutable, canonical values.** `canonical_bytes()` is deterministic (concept tuples sorted, recordstore's canonical JSON); `offer_id` = SHA-256 of it. Never add a field without bumping the record's `"v"` and keeping `from_record` reading old records. Enforced since 2026-08-20: `from_record` dispatches on `"v"` and *raises* on unknown versions, and `to_record` re-encodes each offer in its native version, so old records keep their ids.
- **U3 Clearing trusts no solver.** `MockClearing.submit` asserts the proposal's ontology pin equals its own (step 0 — U10's rehearsal), re-derives every leg against the *current* book and its own ontology — `check_match` for a simple leg, `check_composition` for a composed one (the thing's give moved by an operator give, since 2026-09-13) — re-checks balance (node potentials exist; a simple cycle: product > 1), surplus and fills, and only then commits — all fills under one root (atomicity = one recordstore commit). Any future clearing backend keeps this shape.
- **U4 Solve against pinned roots.** Solvers work on `registry.snapshot()` (a frozen `RecordStore.at`) and pin `ontology_root`/`book_root` in proposals. Reproducibility and auditability beat freshness.
- **U5 Positive rates only.** The loop math is products of positive ratios / sums of logs. There are no negative prices anywhere: disposal is a positively-priced service, emptiness a positively-priced good (see ARCHITECTURE.md §7). Reject any change that introduces signed prices into `Match.rate`.
- **U6 Determinism in the baseline solver.** `ExchangeGraph.find_profitable_loop` iterates nodes/edges in sorted order; the same book must yield the same loop on every replica. Smarter solvers may be stochastic; the baseline may not.
- **U9 Exact rationals in everything clearing re-verifies.** (Entered 2026-09-14 with the v4 record; the id is the plan corpus's.) Quantities, amounts, rates, potentials and surplus are `Fraction`s on the clearing path (`schema.q`), records spell them `n/d` (`schema.rat`), and no epsilon survives in a gate; the solver's `-log` Bellman–Ford search stays floating point because a search is a heuristic and clearing is the truth. A float typed by a person is the decimal it prints as (`99.99` is 9999/100).
- **U7 Vocabulary fails closed.** Unknown categories never match (`Ontology.satisfies` is strict). Silent drift must break loudly.
- **U11 No partially-filled loop survives a merge unnoticed.** (Entered 2026-08-20; the id is fixed by the plan corpus, hence the gap after U7.) Post-merge, every `loop/` record holds a `fill/` for each of its legs — whole (`fill/<offer>`) or, for a divisible give taken in part, per loop (`fill/<offer>/<loop>`, since 2026-09-14) — every fill points at a present loop, no give is filled both whole and in part, and the partial fills of one give sum to at most its quantity (oversold); `verify_loop_atomicity` checks this on every reconciled commit and raises `PartialLoopError`. Checked, not resolved — evicting a cleared loop would be a finality rollback; the deterministic loop-granularity resolver is a registered open problem (`docs/plans/P1-federated-book.md` §3).

## Architecture map (one line per module)

- `src/loopmarket/schema.py` — the offer form: `TimeWindow` (open-ended allowed since v3), `Thing`, `Parts`, `Tokens`, `Offer` (+ `give`/`want` helpers; `ask`/`bid` kept as order-book synonyms), canonical encoding, content-addressed ids, `q`/`rat` (exact numbers, U9). **v4 record (2026-09-14, decided with Peter):** every number a reduced `n/d` string; `step` and `min` on a thing in place of `divisible` (`step` 0 continuous, the whole quantity indivisible, 1 whole apples, 25 sacks; `min` the give-side floor, the chartered bus); a want may be `Parts`, several things all or nothing under one price; `Thing.takes(qty)` is the one quantity rule. v1–v3 re-encode byte for byte. **v3 record (2026-09-12, `docs/plans/P1-spacetime-terms.md`):** no `service`/`where` fields — where and when a thing changes hands are role terms in `Thing.concepts`; `valid` may have no end; `GeoDisc` and the haversine survive only to read and match v1/v2 records among themselves (passing `service`/`where` to `give`/`want` yields a v2 record). No new disc is ever created.
- `src/loopmarket/spacetime.py` — geohash cells: `geohash`, `cell_bounds`, `cell_for_coords` (the finest cell containing a radius — what a bare `LAT,LON,R` becomes); input vocabulary only, ontodag's prefix kind orders the stored name. The day-bucket/cell-prefix chains retired with the `idx/` index (2026-09-12).
- `src/loopmarket/ontology.py` — the catalogue facade: `assert_edge`/`load` to build, `covers`/`satisfies` to query (`known` = a node, or a parametric term of a declared head the DAG can order — computed containment for `from(u2e4x) ⊑ from(u2e)`, and since ontodag #15 a bare place node or a role term naming one, `shop`, `ljubljana`, `my_home_4th`, `from(my_home)`, ordered by the graph; undeclared heads, malformed values and a name outside the dimension fail closed, U7), `persistent()`/`commit()` for pinned roots via `EagerOntoDAG`. **Three relations, declared in the catalogue (Peter, 2026-09-13).** Where and when a thing changes hands are *bare* geo and time terms in the conjunction — `give vegetable-box shop`, a cell, a region, a window, a named time; no `where`/`when` head (they lived one day, 2026-09-12, and were unnecessary). A head stays only for two coordinates of one kind (a route's `from`/`to`, a transport's `depart`/`arrive` — `declare_roles({head: base})`, one edge each) or for a descriptive geo/time term (`made_in`, `made`). **Handover coordinates match when one side contains the other**: the seller delivering anywhere in the city serves the want at the door, the shop serves the buyer collecting anywhere; both directions of `is_below`, never partial overlap. **Categories and descriptive terms match one-way**: the give fits within the want. The seed says which is which: `geo` and `time` hang under the marker `handover` (`declare_handover`; roles under them inherit it), a descriptive head opts out under `descriptive` (`declare_descriptive`) — the two names the core knows besides the dimensions'. **An operator's argument matches want-within-give** (Peter, 2026-09-13 evening: *the parameter of the transport is a want from the transporter's side*): `transport(small-item weight(..8kg))` on the courier's give is what the courier accepts, `transport(bicycle)` on the want is what the wanter hands over, and `bicycle ⊑ small-item` decides — the operator category itself (`transport`, under the marker `operator`, `declare_operator({"transport": ("from", "to")})`) goes the usual way; a conjunction in the argument is several constraints, `transport(A B)` ≡ `transport(A) transport(B)`, and the CLI stores every term in the catalogue's canonical spelling (`surface.elaborate`, U2); a give constraint the want does not answer refuses. One rule under all three: whoever fixes a value states a fact, whoever leaves it open an acceptance, and the fact lies within the acceptance. The operator term is ontodag's graph kind (#19, 0.26.1): `declare_operator` puts the category under `graph-dimension` as well as `operator`, ontodag canonicalises and orders the term, and a spelling it refuses (an unknown or redundant constraint) matches nothing. A head the want does not name constrains nothing; a coordinate the give does not state answers nothing (an internet service has no place). The 2026-09-12 `service-role` marker and its overlap relation ("a handover point exists") were the same idea read as ranges on both sides; partial overlap was the error, not the two directions (`docs/plans/P1-spacetime-terms.md` §3, superseded).
- `src/loopmarket/registry.py` — the book: `offer/`, `sig/`, `withdraw/`, `fill/`, `loop/` keyspace over a duck-typed RecordStore — **no index in the book**: the `idx/{c,t,g}` prefixes (maker books until 2026-08-21, aggregator-derived after, read by nothing throughout) retired 2026-09-12 with the one-query generator — ontodag is the one intersection engine, `docs/plans/ontodag-coupling.md` §5, and the manifest's `index_root` went with it; `snapshot()`, `withdraw()` tombstones, `attach_handoff`/`handoff`/`handoffs`/`loop_of` (the `handoff/` sidecar), `or_set_resolver` for multi-writer merges, `verify_loop_atomicity` (U11), `swarm_offer_book()`.
- `src/loopmarket/announce.py` — the announcement channel (2026-09-14): how a book becomes discoverable — `Announcement(owner, book, role)`, latest per owner, retractions; three backends behind one protocol, chosen by spec like books: `chain:RPC_URL@CONTRACT` (the `LoopBookRegistry` event log on the EVM chain Swarm settles on — Gnosis today; nothing chain-specific in contract or code; `contracts/LoopBookRegistry.sol`, ABI beside it, `scripts/deploy_registry.py`; **deployed 2026-09-14 on Gnosis at `0xD4379E494a488411D964BebDb210C0bf628d97af`**, first announcement read back through the chain the same day; web3 lazy behind the `chain` extra, B2), `file:PATH` (sessions on one machine), `memory:`; several comma-separated are one channel (`UnionAnnouncements`, the newer chain last) so a chain move is a setting. `msg.sender` is the owner, the feed-signing key, so the announcement authenticates the book (U8). ## Known simplifications (deliberate; each has a roadmap home)

1. **Divisibility caveat.** The product condition (Π rates > 1 around a cycle) prices out exactly only when quantities can scale so per-node token balances cancel. Indivisible legs get the conservative `per_node_ok` gate in clearing. Proper clearing pricing (choosing actual prices between each give and want, distributing surplus) is P2 — now specified: equal log-surplus split under uniform directional clearing (`docs/plans/P2-clearing-pricing.md`); the divisible/indivisible line is the LP/ILP complexity boundary (`docs/plans/P2-loop-selection.md`). **Composition decided 2026-09-07** (`P2-loop-selection.md` §10): one want may be satisfied by several unconditional gives — by operator along a dimension (transport moves place, storage moves time, exchange moves denomination) or by aggregation along quantity (six lifters) — the conjunction lives in the single want so all-or-nothing is free, and the buyer's divisible money give is split at clearing; give-side bundles stay excluded. **Declared parts decided 2026-09-12, built 2026-09-14 on the v4 record** (`P2-loop-selection.md` §10, `cli.md` §13): the buyer names the parts (`draft`/`+`/`offer` at the CLI, `Parts` in the API), the want publishes as one v4 offer, `check_parts` is its exact check, `parts_legs` the baseline search, and the fill names which give served which part with the quantity taken; no prices on parts, no cross-part constraints, drafts never enter the book. The give side gets a *floor*, never parts — the chartered bus, the cow: a minimum fill on one give, the mirror of aggregation, a flow lower bound (`Thing.min`, v4; the CLI spelling `10kg..` on a give is not wired yet); the kit is one indivisible thing; heterogeneous give bundles stay the shut door (the reseller is the route). **Granularity decided 2026-09-14:** `step` replaces the boolean. **Partial fills built the same day:** a fill takes exactly the want's quantity from a divisible give and the remainder stays open (`OfferRegistry.available`/`taken`/`loops_of`; matching takes `available=`, the agent passes `book.availability`, clearing re-derives against its own book's remainders), the fills of one give are keyed per loop and may not sum past its quantity (U11), and a remainder below the floor or one step is dust that exhausts the offer (`Thing.exhausted`; the U13 rule). So the stepped clearing regime is the exact one, (a): no rounding, ever — the LP with rounding is not needed while fills are the wants' own quantities. **Aggregation by quantity built the same day** (the six lifters): `Leg.quantities` carries an aggregated leg's shares, `check_aggregate` is its exact check (each share within what that give may give, the shares summing to the want's quantity), `aggregate_legs` the deterministic depth-first baseline search over the gives of the want's thing, wired into the agent beside the operator and parts searches; clearing re-derives the split, and the fill names every give with its share. **The baseline solver composes since 2026-09-13** (Peter: *the whole point of a solver is to find circulations*): `Leg` (one want, one or more gives), `check_composition` (the thing's give moved by an operator give — a category under `operator`, `declare_operator({"transport": ("from", "to")})`, whose argument the thing must fit (`Ontology.accepts`: the box goes with the small-item courier, the piano does not — the payload check, 2026-09-13 evening) and whose input end is comparable with the thing's coordinate, its output replacing it), `Circulation` (a set of legs in which every maker both gives and receives; feasibility = node potentials exist, the dual of §11; `surplus` compounds the uniform per-leg gain and equals `Loop.surplus` on a cycle; `loop_id` agrees with `Loop` there) and `find_circulations` (deterministic depth-first, after Bellman–Ford's simple cycles). Clearing re-derives composed legs; the `loop/` record's legs carry `gives` and the set its `potentials`. One hop, one operator per leg; `examples/delivery.loop` clears the grocer's box at the shop plus the courier's run to the door. The reseller form (courier wants the box at the shop, gives it at the door) also clears as a plain cycle and is the *maker's* choice; §10's reason to prefer composition stands (unconditional offers).
2. **Candidate generation is O(gives×wants) by default.** Correct and fine in memory. **The dimension-backed generator landed 2026-07-30** (`src/loopmarket/dimensions.py`): `DimensionIndex` + `candidate_matches_indexed`, recall-exact vs the baseline (tests/test_dimensions.py); the index is a derived deepcopy of the catalogue — never file offers into the shared catalogue, that would churn pinned roots. **The want's categories are the query (2026-09-12/13):** `candidates` is exactly one `get([line marker, *one-way terms], items_only=True)` — an operator term filed and queried as its category, its argument the exact check's — ontodag's planner orders the cones and loopmarket does no set arithmetic on the answer (`docs/plans/ontodag-coupling.md` §5); `items_only` is ontodag #14's surviving half. Handover coordinates are left to `check_match`: a give that *contains* the want's place (the city-wide seller) sits above the want's term, not in its cone, and loopmarket does not stitch a downward and an upward walk together — the ask upstream, when book sizes want place pruning, is a query term meaning "comparable to X" (`ontodag-coupling.md` §7). Gives are filed under exactly the terms they carry plus a private record-line marker (a disc is not a cell: `check_match` refuses v2×v3 pairs); the v1/v2 window and disc are fields the exact check gates, not terms. The day's detours — three queries intersected in Python, ontodag #14's `overlapping=` planner argument, a whole-space value for roles a give is silent on — are all withdrawn: overlap was a modelling error, not a missing operator. Suite 54 s → 11 s. The baseline remains the default in `SolverAgent` and the recall benchmark; wire the indexed generator into the solver when book sizes ask for it.
3. **Geo cells: the truth for v3, a hint for v2.** Since the v3 record (2026-09-12) a place *is* a cell, a place node under a cell, or a region node above cells, and containment on it is exact (the graph's, since ontodag #15 landed the same night: `ljubljana` stands in the offer as a bare term and the exact covering of a place is a region node whose covering is a lower bound — CONTRACT G2); `LAT,LON,R` input becomes the finest cell containing the radius, so a place near a cell edge names the coarser cell unless a region names its covering. Peter's covering-as-a-value (`where(u24m+u24q)`, no node, no name) is deferred upstream to the anonymity tripwire (ontodag DIMENSIONS.md §14). For v1/v2 records the disc is the truth. Neighbour-cell fan-out or S2 coverings: P1, only if profiling says so.
4. **Single shared book in the demo.** The decentralized shape is one book per maker (own feed, own signer), aggregated with `RecordStore.merge` under `or_set_resolver`. The key layout is already identical; the aggregator loop is P1 — now specified end-to-end (announcement channel, aggregator manifest, merge discipline incl. the fill-determinism and loop-granularity fixes, tombstones, postage economics) in `docs/plans/P1-federated-book.md`. Note the 2026-08-07 demotion: the *shared* Swarm book (one feed, many writers) is a dev/demo tool only — feed CAS is best-effort, so one-signer-per-feed is the safety model.
5. **`bond`, `oracle`, `arbitrator` are carried, not enforced.** They are in the canonical encoding from day one so ids don't churn when P3 lands (bond escrow, oracle adapters, arbitration hooks, bonded ontology assertions — `Ontology.assert_edge` already takes `bond=`). **The P3 mechanism design now has a dedicated sister repo (2026-08-01): factbond** (github.com/petfold/factbond — bonded assertions/optimistic adjudication, odds-weighted bonds, shared bond pool, information insurance). Adopt, don't redesign: the loopmarket coupling (clearing-attached insurance on the ⊑ edges a loop relied on; per-edge loss experience as the catalogue reliability audit; certificates clearing the structural half of disputes) is worked out in factbond's `docs/INTEGRATION.md` §8 and ARCHITECTURE.md §4's update note here.
6. **Batch auctions absent.** MockClearing is first-valid-wins. The P2 beat is now specified (sealed proposals, numeraire-free scoring, fairness floor, capped marginal-contribution rewards, baseline as reserve bid) in `docs/plans/P2-batch-auction.md`.
7. **No privacy layer.** Offers are plaintext. Coarse-first disclosure, commitments, ZK fits-within proofs: P4 — now staged in `docs/plans/P4-privacy.md`; its Tier 1 needs no new cryptography, and its format-freeze list constrains P2 record formats. Do not add ad-hoc encryption before that design lands.

## Conventions

- `src/` layout; tests via pytest from the repo root (conftest handles the path).
- Names are identity at public boundaries (strings accepted where objects are), matching ontodag.
- Docstrings explain *why* (the design decision), comments explain *why not* (the rejected alternative). Keep both current when changing behaviour.
- One invariant, one commit — mirror ontodag's fix history style.
- **Vocabulary (2026-09-07): loop, cycle, circulation.** A *loop* is any cleared circulation — the essay's word and the name in code (`Loop`, `LoopProposal`, `loop/`, `loop_id`). A *cycle* (or simple loop) is the strict circle, which is all the P0 solver can find and all today's `Loop` can hold; use it wherever the reasoning depends on going round (products around it, negative cycles, cycle packing). *Circulation* is the technical term when the flow theory is invoked (`docs/plans/P2-loop-selection.md` §11). Audit of the corpus done 2026-09-07; new text follows the rule.
- **Vocabulary (renamed 2026-09-07): clearing ≠ settlement.** *Clearing* is the atomic commit that turns a solver's proposal into fixed obligations (`clearing.py`, `MockClearing`, U3). *Settlement* is the makers actually delivering — P3's oracles, bonds and factbond. *Commit* is only the recordstore/chain write. The `loopmarket.settlement` import alias, kept one release, was removed 2026-09-14. `P2-clearing-pricing.md` (ex `P2-settlement-pricing.md`) follows the rename in full; the rest of the plan corpus under `docs/plans/` and `ARCHITECTURE.md` predate it and still say "settlement" for the clearing step — read them with that mapping, and use the new words in anything you write. factbond and ontodag's docs were updated the same day.
